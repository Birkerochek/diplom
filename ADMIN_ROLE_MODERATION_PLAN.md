# План внедрения роли администратора и контура модерации

## 1. Цель доработки

Добавить в систему отдельный защищённый административный контур, в котором администратор управляет безопасностью и качеством данных платформы, а публикация мероприятий проходит обязательную модерацию.

Ключевые цели:

- организатор больше не публикует мероприятие напрямую;
- после создания мероприятие получает статус **«на модерации»**;
- организатор явно видит сообщение **«Мероприятие отправлено на модерацию»**;
- администратор может одобрить или отклонить мероприятие;
- при отклонении причина обязательна и видна организатору;
- все критические действия администратора защищены проверкой роли `admin`, логируются и требуют подтверждения там, где есть риск;
- администратор управляет не только модерацией мероприятий, но и пользователями, ролями, блокировками, жалобами, категориями, верификацией организаторов, лимитами, аудитом и платформенными настройками.

---

## 2. Текущее состояние системы и разрыв

Сейчас в проекте фактически реализованы только два рабочих контура:

- volunteer;
- organizer.

По модели мероприятия система сейчас опирается на единый жизненный статус без полноценной модерации. Организатор может управлять статусом мероприятия напрямую, а волонтёр видит только опубликованные состояния.

Проблемы текущего состояния:

1. Нет отдельного защищённого admin-контура.
2. Нет отдельной роли `admin` с полным доступом к административным функциям.
3. Нет очереди модерации.
4. Нет причины отклонения и истории решений.
5. Нет конфликтоустойчивой обработки действий нескольких модераторов.
6. Нет обязательного аудита критических действий.
7. Нет инструментов платформенного управления: жалобы, лимиты, верификация, справочники, настройки.

## 3. Целевая ролевая модель

### 3.1. Базовые роли пользователей

Для проекта достаточно трёх ролей:

- `volunteer` — участвует в мероприятиях;
- `organizer` — создаёт и ведёт мероприятия;
- `admin` — единая административная роль с полным доступом ко всем административным функциям.

### 3.2. Упрощённая модель доступа

Для текущей реализации не нужно вводить дополнительные административные подроли и внутренние матрицы доступа.

Достаточно простой схемы:

1. если `User.role = volunteer`, пользователь работает только в волонтёрском контуре;
2. если `User.role = organizer`, пользователь работает только в контуре организатора;
3. если `User.role = admin`, пользователь получает полный доступ ко всем страницам и операциям административного контура.

### 3.3. Как трактовать доступ в этой версии

В этой итерации админский доступ строится только на одной роли `admin`.

Правило доступа:

- `role !== admin` -> нет доступа в `/admin/*` и ко всем admin API;
- `role === admin` -> полный доступ к модерации, пользователям, жалобам, верификации, лимитам, аудитам, справочникам и настройкам платформы.

### 3.4. Почему такой вариант лучше для текущего этапа

Этот вариант лучше подходит для текущего проекта, потому что:

- проще реализуется в существующей архитектуре;
- не требует дополнительных таблиц ролей и permissions;
- быстрее покрывает бизнес-потребность в модерации и администрировании;
- снижает объём backend- и frontend-логики;
- при необходимости позже может быть расширен до более детального разграничения.

## 4. Обновлённая модель статусов мероприятия

### 4.1. Рекомендуемый практический вариант для реализации

Чтобы внедрить модерацию с минимальным риском для текущей архитектуры, рекомендуется сохранить **единый статус мероприятия**, но расширить его.

Новый `EventStatus`:

- `draft` — черновик;
- `pending_moderation` — на модерации;
- `rejected` — отклонено;
- `active` — одобрено и доступно волонтёрам;
- `suspended` — одобрение отозвано администратором, мероприятие скрыто;
- `completed` — завершено;
- `cancelled` — отменено;
- `archived` — архивировано.

### 4.2. Смысл статусов

| Статус | Кто видит | Что означает |
|---|---|---|
| `draft` | организатор, админ | черновик, ещё не отправлен |
| `pending_moderation` | организатор, админ | ждёт решения модератора |
| `rejected` | организатор, админ | отклонено, требуется исправление |
| `active` | все по правилам доступа | одобрено и доступно для регистрации волонтёров |
| `suspended` | организатор, админ | ранее было одобрено, но скрыто после вмешательства администратора |
| `completed` | все по правилам доступа | мероприятие завершено |
| `cancelled` | организатор, админ, при необходимости зарегистрированные волонтёры | мероприятие отменено |
| `archived` | админ, организатор при просмотре архива | выведено из оперативной работы |

### 4.3. Основные переходы статусов

| Откуда | Куда | Кто выполняет | Условие |
|---|---|---|---|
| `draft` | `pending_moderation` | организатор | отправка на модерацию |
| создание мероприятия | `pending_moderation` | система | основной пользовательский сценарий создания |
| `pending_moderation` | `active` | админ | одобрение |
| `pending_moderation` | `rejected` | админ | отклонение с причиной |
| `rejected` | `pending_moderation` | организатор | повторная отправка после исправлений |
| `active` | `suspended` | админ | отзыв одобрения |
| `suspended` | `pending_moderation` | организатор | исправления и повторная отправка |
| `active` | `completed` | система/организатор | завершение мероприятия |
| `active` | `cancelled` | организатор/админ | отмена |
| `completed` | `archived` | админ | архивирование |
| `cancelled` | `archived` | админ | архивирование |
| `rejected` | `archived` | админ | архивирование старой версии / закрытие кейса |

### 4.4. Обязательные бизнес-правила по видимости

1. Волонтёр **никогда** не видит `draft`, `pending_moderation`, `rejected`, `suspended`, `archived`.
2. Организатор видит **все свои** мероприятия, включая отклонённые и скрытые.
3. Администратор видит все данные и все функции административного контура.
4. Регистрация волонтёра разрешена только для `active`.
5. `pending_moderation` и `rejected` не участвуют в публичной выдаче, поиске и рекомендациях.

## 5. Бизнес-флоу модерации мероприятия

### 5.1. Создание организатором

Основной сценарий:

1. Организатор заполняет форму создания мероприятия.
2. Нажимает основное действие: **«Отправить на модерацию»**.
3. Система создаёт мероприятие со статусом `pending_moderation`.
4. Система создаёт запись в истории модерации.
5. Организатор после успешного создания видит:
   - статус-бейдж **«На модерации»**;
   - системное сообщение **«Мероприятие отправлено на модерацию»**;
   - подсказку, что до решения администратора мероприятие не отображается волонтёрам.

Дополнительный необязательный сценарий для MVP+:

- можно оставить действие **«Сохранить как черновик»**, но основной CTA должен вести именно в модерацию.

### 5.2. Очередь модерации у администратора

Администратор заходит в раздел очереди модерации и видит:

- список мероприятий в `pending_moderation`;
- дату отправки;
- организатора;
- категорию;
- признаки риска;
- информацию о предыдущих отклонениях;
- фильтры: дата, категория, организатор, повторная отправка, срочность, назначенный модератор.

### 5.3. Одобрение

При одобрении администратор:

1. открывает карточку мероприятия;
2. сверяет содержание, дату, место, лимиты и требования;
3. нажимает **«Одобрить»**;
4. подтверждает опасное действие в модальном окне;
5. система:
   - меняет статус на `active`;
   - сохраняет кто и когда одобрил;
   - закрывает активную модерационную заявку;
   - создаёт уведомление организатору;
   - пишет аудит-запись.

### 5.4. Отклонение

При отклонении администратор:

1. нажимает **«Отклонить»**;
2. обязан указать причину;
3. при необходимости выбирает шаблон причины + дописывает комментарий;
4. система:
   - меняет статус на `rejected`;
   - сохраняет причину отклонения;
   - фиксирует модератора и время решения;
   - создаёт уведомление организатору;
   - пишет аудит-запись.

### 5.5. Что видит организатор после решения

#### После одобрения

Организатор видит:

- статус `active`;
- сообщение: **«Мероприятие одобрено и опубликовано»**;
- дату и время решения;
- при необходимости комментарий администратора.

#### После отклонения

Организатор видит:

- статус `rejected`;
- сообщение: **«Мероприятие отклонено модератором»**;
- обязательный блок **«Причина отклонения»**;
- кнопку **«Исправить и отправить повторно»**.

### 5.6. Повторная отправка после отклонения

Сценарий:

1. Организатор открывает отклонённое мероприятие.
2. Исправляет данные.
3. Нажимает **«Отправить повторно на модерацию»**.
4. Система:
   - переводит мероприятие в `pending_moderation`;
   - создаёт новую модерационную заявку с новой ревизией;
   - сохраняет связь с предыдущими решениями;
   - очищает текущую «активную причину отклонения» из карточки, но оставляет историю.

## 6. Edge cases и правила обработки исключений

### 6.1. Повторная отправка после отклонения

Правило:

- каждая повторная отправка создаёт **новую ревизию модерации**, а не переписывает историю прошлого решения.

### 6.2. Конфликт модераторов

Проблема:

- одно и то же мероприятие открыли два администратора.

Решение:

- на уровне записи модерации вводится `version` для optimistic locking;
- дополнительно вводятся `claimedById`, `claimedAt` для мягкой блокировки;
- при попытке второго модератора принять решение по уже изменённой заявке backend возвращает `409 Conflict`;
- интерфейс показывает: **«Заявка уже обработана другим модератором»**.

### 6.3. Отмена одобрения

Сценарий нужен, если после публикации нашли нарушение.

Решение:

- администратор переводит мероприятие из `active` в `suspended`;
- обязательно указывает причину отзыва одобрения;
- мероприятие скрывается из выдачи волонтёрам;
- организатор получает уведомление;
- если уже есть регистрации волонтёров, дополнительно формируются уведомления участникам и карточка последствий.

### 6.4. Архивирование

Архивирование нужно для вывода кейсов из оперативной работы, а не для физического удаления.

Правило:

- архивируются `completed`, `cancelled`, устаревшие `rejected`, `suspended`;
- в архиве записи доступны по аудиту и поиску администратора;
- физическое удаление мероприятий из админки не допускается как стандартная операция.

### 6.5. Массовые проверки

Разрешены только администратору и только для событий низкого риска.

Ограничения:

- массовое одобрение — допустимо для выбранных карточек;
- массовое отклонение — только с общей причиной и отдельным подтверждением;
- по итогам массовой операции формируется отчёт: успешно / пропущено / конфликт / ошибка валидации.

### 6.6. Организатор заблокирован во время модерации

Если организатор заблокирован:

- его pending-заявки можно автоматически переводить в отдельный флаг риска;
- финальное решение по мероприятию принимается администратором с учётом блокировки;
- создание новых мероприятий запрещается.

### 6.7. Срок устаревания решения

Если мероприятие долго висит в `pending_moderation` и дата проведения уже прошла:

- система помечает его как просроченное в очереди;
- админ может отклонить по шаблону «Дата мероприятия уже неактуальна» или архивировать.

## 7. Сущности, которыми должен управлять администратор

Ниже перечислены сущности, обязательные для безопасной и управляемой платформы.

### 7.1. Пользователи

#### Что администратор просматривает

- профиль пользователя;
- роль;
- статус активности;
- историю входов и ключевые действия;
- связанные мероприятия / регистрации / жалобы / блокировки.

#### Что может изменять

- активность аккаунта (`active`, `blocked`, `suspended`);
- причину блокировки;
- срок блокировки;
- системные флаги риска.

#### Что может ограничивать

- вход в систему;
- создание мероприятий;
- регистрацию на мероприятия;
- доступ к части функциональности.

#### Влияние на систему

- снижает риск злоупотреблений;
- позволяет быстро реагировать на нарушения;
- обеспечивает управляемость спорных кейсов.

### 7.2. Роли и блокировки

#### Что администратор просматривает

- текущую роль пользователя (`volunteer`, `organizer`, `admin`);
- историю смены ролей;
- активные блокировки;
- ограничения и причины ограничений.

#### Что может изменять

- переводить пользователя между ролями `volunteer`, `organizer`, `admin`;
- временно блокировать пользователя;
- снимать блокировку;
- фиксировать причину и срок ограничения.

#### Влияние на систему

- позволяет централизованно управлять доступом к платформе;
- упрощает администрирование без дополнительной внутренней матрицы прав.

### 7.3. Жалобы

Жалобы нужны на:

- мероприятие;
- организатора;
- волонтёра;
- комментарий/коммуникацию, если модуль будет добавлен позже.

#### Что администратор просматривает

- текст жалобы;
- заявителя;
- объект жалобы;
- вложения;
- историю обработки.

#### Что может изменять

- статус жалобы (`new`, `in_review`, `resolved`, `rejected`, `escalated`);
- итоговое решение;
- применённые меры.

#### Что может ограничивать

- блокировать пользователя;
- скрывать мероприятие;
- отзывать одобрение мероприятия;
- эскалировать кейс старшему администратору.

#### Влияние на систему

- даёт канал контроля качества и безопасности;
- снижает репутационные риски.

### 7.4. Категории мероприятий / справочники

В текущем проекте это логично опирать на справочник категорий/активностей.

#### Что администратор просматривает

- список категорий;
- порядок отображения;
- активность категории;
- использование в мероприятиях.

#### Что может изменять

- создавать категорию;
- редактировать название, slug, иконку, цвет;
- отключать категорию;
- менять порядок.

#### Что может ограничивать

- запрещать использование невалидных категорий;
- отключать устаревшие направления.

#### Влияние на систему

- улучшает качество данных;
- упрощает фильтрацию и аналитику;
- уменьшает хаос в пользовательском вводе.

### 7.5. Верификация организаторов

Это отдельный обязательный контур доверия.

#### Что администратор просматривает

- данные организации;
- контактные лица;
- документы;
- историю заявок на верификацию;
- риск-флаги и прошлые нарушения.

#### Что может изменять

- статус верификации (`pending`, `verified`, `rejected`, `revoked`);
- срок действия верификации;
- комментарий к решению.

#### Что может ограничивать

- запрет публикации мероприятий без верификации;
- дополнительные лимиты для неверифицированных организаторов.

#### Влияние на систему

- повышает доверие волонтёров к платформе;
- снижает риск мошеннических мероприятий.

### 7.6. Лимиты

Лимиты нужны для борьбы со спамом и перегрузкой модерации.

#### Что администратор просматривает

- текущие лимиты платформы;
- индивидуальные override-лимиты;
- фактическое потребление лимитов организаторами.

#### Что может изменять

- число активных мероприятий на организатора;
- число отправок на модерацию в сутки;
- число массовых операций;
- лимиты для неверифицированных организаторов.

#### Влияние на систему

- стабилизирует нагрузку;
- ограничивает злоупотребления;
- управляет SLA модерации.

### 7.7. Аудит действий

#### Что администратор просматривает

- кто, когда и что сделал;
- над какой сущностью;
- старое и новое значение;
- IP / user-agent / correlation id.

#### Что может делать

- искать по журналу;
- выгружать отчёты;
- расследовать инциденты;
- подтверждать правомерность действий сотрудников.

#### Влияние на систему

- обязательная основа безопасности и расследования спорных действий.

### 7.8. Платформенные настройки

#### Что администратор просматривает

- глобальные правила публикации;
- шаблоны причин отклонения;
- SLA модерации;
- настройки уведомлений;
- признаки обязательной верификации.

#### Что может изменять

- список причин отклонения;
- включение/выключение автоправил;

## 9. Backend: требования к API

### 9.1. Общие принципы

1. Любой admin-endpoint обязан проверять:
   - авторизацию;
   - `user.role = admin`.
2. Любое критическое действие должно:
   - быть идемпотентным при повторном запросе;
   - писать аудит-запись;
   - возвращать понятный код конфликта при гонке.
3. Доступ к административным данным нельзя обеспечивать только скрытием кнопок на UI — backend обязан жёстко проверять роль `admin`.

### 9.2. Organizer API

#### Создание мероприятия

`POST /api/events`

Новые требования:

- по умолчанию создавать мероприятие в `pending_moderation`;
- проставлять `submittedForModerationAt`;
- создавать `EventModerationRequest`;
- возвращать флаг:
  - `status = pending_moderation`
  - `moderationMessage = "Мероприятие отправлено на модерацию"`

#### Повторная отправка

`POST /api/organizer/events/:eventId/resubmit`

Поведение:

- доступно только для `rejected` и `suspended`;
- переводит в `pending_moderation`;
- создаёт новую запись модерации;
- увеличивает `moderationIteration`.

#### Получение статуса модерации

`GET /api/organizer/events/:eventId/moderation`

Должно возвращать:

- текущий статус;
- последнюю причину отклонения/отзыва;
- историю решений;
- дату отправки;
- дату последнего решения;
- имя/идентификатор модератора, если это допустимо политикой платформы.

### 9.3. Admin API: модерация мероприятий

#### Очередь модерации

`GET /api/admin/moderation/events`

Фильтры:

- `status`
- `claimedBy`
- `organizerId`
- `activityType`
- `dateFrom/dateTo`
- `isResubmitted`
- `riskLevel`
- `page/perPage`

#### Детализация заявки

`GET /api/admin/moderation/events/:eventId`

Возвращает:

- полную карточку мероприятия;
- текущую заявку на модерацию;
- историю прошлых решений;
- риск-флаги;
- жалобы, если есть;
- действия, доступные текущему администратору.

#### Взять в работу

`POST /api/admin/moderation/events/:eventId/claim`

Нужно для мягкой блокировки и распределения очереди.

#### Одобрить

`POST /api/admin/moderation/events/:eventId/approve`

Требования:

- проверка `version` или active moderation request id;
- подтверждение, что заявка ещё pending;
- создание audit-записи;
- создание notification-события.

#### Отклонить

`POST /api/admin/moderation/events/:eventId/reject`

Требования:

- поле `reason` обязательно;
- сохраняется reason code и свободный текст;
- создаются audit и notification.

#### Отозвать одобрение

`POST /api/admin/moderation/events/:eventId/revoke`

Требования:

- доступно только для `active`;
- причина обязательна;
- если есть регистрации — вернуть последствия в ответе API;
- запуск уведомлений организатору и зарегистрированным волонтёрам.

#### Массовое одобрение

`POST /api/admin/moderation/events/bulk-approve`

#### Массовое отклонение

`POST /api/admin/moderation/events/bulk-reject`

Ответ должен быть пакетным:

- список успешных;
- список конфликтов;
- список пропусков;
- причины отказов.

## 14. Требования к backend-правилам безопасности

1. Проверка роли `admin` должна быть и в UI, и на сервере, но истинный контроль — только на сервере.
2. Все критические admin-операции должны хотя бы логироваться на сервере через стандартные application logs.
3. Любая запись модерации должна быть неизменяемой после финального решения, кроме системного архивирования.
4. Все операции изменения статуса должны выполняться транзакционно.
5. Массовые операции должны иметь частично успешный результат и детальный отчёт.
6. Для конфликтов модераторов нужен optimistic locking.
7. Для опасных операций должна сохраняться причина действия.
8. Заблокированный пользователь не должен получать доступ даже при валидной сессии без дополнительной серверной проверки статуса аккаунта.

## 16. Критерии приёмки для QA

### 16.1. Роль и доступы

1. Пользователь без роли `admin` не может открыть `/admin/*`.
2. Пользователь с ролью `admin` получает доступ ко всем разделам admin-контура.
3. Backend admin-endpoint возвращает `403`, если `role != admin`.
4. Заблокированный администратор не может войти в admin-контур.

### 16.2. Создание и модерация мероприятий

5. После создания организатором мероприятие получает статус `pending_moderation`.
6. После создания организатор видит текст **«Мероприятие отправлено на модерацию»**.
7. Мероприятие в `pending_moderation` не видно волонтёрам в списке и по прямой ссылке.
8. Администратор видит новое мероприятие в очереди модерации.
9. Администратор может одобрить pending-заявку, и после этого мероприятие становится `active`.
10. После одобрения организатор получает уведомление и видит обновлённый статус.
11. Администратор может отклонить pending-заявку только с обязательной причиной.
12. После отклонения организатор видит статус `rejected` и полную причину отклонения.
13. Организатор может исправить отклонённое мероприятие и отправить его повторно.
14. После повторной отправки создаётся новая запись истории модерации.

### 16.3. Безопасность и гонки

15. Если два модератора одновременно принимают решение по одной заявке, только один запрос проходит успешно, второй получает `409 Conflict`.
16. Любое одобрение, отклонение, отзыв одобрения пишется в аудит.
17. Организатор не может самостоятельно перевести мероприятие в `active` через API.
18. Заблокированный организатор не может создать новое мероприятие и отправить повторно отклонённое.

### 16.4. Отзыв одобрения и последствия

19. Администратор может отозвать одобрение только у `active`-мероприятия.
20. При отзыве одобрения обязательна причина.
21. После отзыва мероприятие исчезает из публичной выдачи волонтёров.
22. Организатор получает уведомление об отзыве.
23. Если на мероприятие уже есть регистрации, зарегистрированные волонтёры получают уведомления о последствиях.

### 16.5. Архив и массовые операции

24. Архивированные мероприятия по умолчанию не отображаются в рабочих списках.
25. Массовое одобрение/отклонение доступно только пользователю с ролью `admin`.
26. После массовой операции система возвращает детальный отчёт по всем выбранным записям.

### 16.6. Интерфейсы

27. В админке опасные действия требуют подтверждения.
28. В карточке организатора отображаются:
   - текущий статус;
   - дата отправки на модерацию;
   - дата последнего решения;
   - причина отклонения/отзыва, если есть.
29. В списке мероприятий организатора доступны фильтры по новым статусам.
30. Волонтёр по-прежнему может зарегистрироваться только на `active`-мероприятие.

---

## 17. Рекомендуемое решение для разработки без лишнего переусложнения

Если нужно внедрять функциональность поэтапно, оптимальный MVP-порядок такой:

1. добавить `admin` в роль пользователя;
2. ввести `pending_moderation`, `rejected`, `suspended`, `archived` в статус мероприятия;
3. добавить `EventModerationRequest` и `AuditLog`;
4. закрыть прямое управление публикацией организатором;
5. реализовать admin moderation queue и решения approve/reject;
6. показать организатору статус и причину решения;
7. затем расширить контур до жалоб, верификации, лимитов и настроек.

Такой порядок даёт быструю бизнес-ценность и не ломает существующую архитектуру слишком резко.

---

## 18. Финальный ожидаемый результат

После внедрения система должна работать так:

- организатор создаёт мероприятие и сразу отправляет его на модерацию;
- в интерфейсе он видит сообщение **«Мероприятие отправлено на модерацию»**;
- до решения администратора мероприятие не публикуется волонтёрам;
- администратор в защищённой админке берёт заявку в работу, одобряет или отклоняет её;
- при отклонении причина обязательна и прозрачно отображается организатору;
- при повторной отправке сохраняется полная история модерации;
- все критические действия защищены проверкой роли `admin`, журналируются и подтверждаются;
- администратор управляет не только модерацией, но и безопасностью, качеством и управляемостью платформы целиком.
